# Poseidon development mock-data mode

Status: **implemented on #24**, switcher added on follow-up work
Tracking issue: **#24 — Dev mode: temporary seeded mock history with zero Firebase initialization**

This is development tooling only. It runs the real Poseidon application against deterministic, disposable personal-history data without signing in or initializing Firebase.

## Launch

There is one development site and one command:

```bash
npm run dev
```

By default this boots the **real** application, exactly as production does: Firebase, the auth gate, sign-in.

Switch to seeded history from inside the app. The development badge in the bottom-right corner shows what is currently loaded and opens the picker:

```text
Boot with
  Real · Firebase     sign-in
  Mock · 0            empty
  Mock · 3            3 dives
  Mock · 5            5 dives
  Mock · 15           15 dives
  Mock · 30           30 dives

  Mock history is in memory only. Reloading re-seeds it.
```

Choosing an entry stores the choice and reloads. The badge is present in both worlds, so switching back to the real application never requires editing a URL or restarting the server.

The choice is stored in `localStorage` under `poseidon.dev.selection` and survives reloads and restarts until it is changed.

### URL parameter

Scripts and bookmarks can still set the selection directly. The parameter wins over the stored choice and is then persisted:

```text
http://localhost:5173/?mock=0#/
http://localhost:5173/?mock=3#/
http://localhost:5173/?mock=5#/
http://localhost:5173/?mock=15#/
http://localhost:5173/?mock=30#/
http://localhost:5173/?mock=off#/
```

Presets are `0`, `3`, `5`, `15` and `30`; `off` (or `real`) returns to the real application. Unsupported values fall back to 15 with a development-console warning.

Resolution order is **query parameter → stored choice → real application**.

## Stale service workers

Poseidon is a PWA, so a production build, `npm run preview`, the PWA probes or an installed PWA can leave a service worker registered on an origin. A worker registered on the development origin keeps serving its precached **production** bundle on top of the development server, and the failure is completely silent: no console error, no development badge, `?mock=` ignored, and source edits that never appear — because development code is never fetched at all.

Application code cannot repair this, because the stale worker is what stops that code from loading. The development server therefore answers the worker-update fetch itself. `developmentServiceWorkerReset()` in `apps/web/vite.config.ts` serves a worker at `<base>sw.js` that clears every cache, unregisters itself and reloads open tabs onto the real development server. Browsers re-fetch the worker script over the network on navigation, so an affected tab repairs itself on the next load.

The plugin is `apply: 'serve'`, so it exists only on the development server. Production still ships the real precaching worker generated by VitePWA, and `npm run test:pwa` still proves the production shell is controlled and cold-starts offline.

As a belt-and-braces measure, `registerPoseidonServiceWorker()` in `apps/web/src/pwa-registration.ts` also releases any worker and its caches when `import.meta.env.DEV` is true, rather than registering one. That path only runs once development code is loading, so the server-side reset above is the part that breaks the deadlock.

## Hard Firebase boundary

Mock mode is selected only when both are true:

- Vite is serving a development build (`import.meta.env.DEV`);
- the resolved development selection is `mock`.

`apps/web/src/main.tsx` makes that decision before loading either application root. The `import.meta.env.DEV` guard is written inline so that Vite's build-time replacement makes the whole development block unreachable and removable.

```text
bootstrap
  |
  +-- production (import.meta.env.DEV === false)
  |     -> the entire development block is removed at build time
  |     -> dynamic import AuthProvider + AuthGate
  |     -> FirestorePersistence
  |     -> PoseidonProvider
  |     -> App
  |
  +-- DEV
        -> dynamic import dev/selection + dev/DevModeBadge
        -> resolve selection: ?mock= -> localStorage -> real
        |
        +-- selection = real
        |     -> dynamic import AuthProvider + AuthGate
        |     -> FirestorePersistence
        |     -> PoseidonProvider + App + badge
        |
        +-- selection = mock
              -> dynamic import mock-data
              -> MemoryPersistence
              -> deterministic seed
              -> PoseidonProvider + App + badge
```

The preset vocabulary and the `?mock=` parser live in `apps/web/src/dev/selection.ts`, deliberately free of domain imports, so that deciding what to boot never loads the seeded history.

The shared application no longer imports the Firebase-backed `AuthProvider` through `DataAndBackup`; the non-Firebase auth context contract lives separately in `apps/web/src/auth/AuthContext.tsx`.

Consequences in mock mode:

- Firebase configuration is not imported;
- Firebase Auth is not initialized;
- no Google auth listener or popup exists;
- no `approvedUsers` lookup occurs;
- `FirestorePersistence` is not constructed;
- no Firestore/Firebase request is made;
- a production build cannot enter mock mode, and cannot render the badge, whatever is stored in `localStorage` or passed as `?mock=30`.

## Persistence and reset semantics

Mock personal history uses the domain package's `MemoryPersistence`, through the same `PersistenceAdapter -> PoseidonStore -> PoseidonClient` seam as the rest of the app.

During the current page session, all normal store behavior works:

- create/edit/delete dives;
- user-created creatures;
- derived Home/Journal/Collection/Atlas state;
- export;
- restore merge/replace.

No mock personal-history state is written to localStorage or Firestore.

A reload constructs a fresh in-memory store and reapplies the selected seed. Any edits, deletes, new dives or restores from the previous page session disappear by design. Switching presets from the badge is a reload, so it discards session edits in exactly the same way.

The selection itself is the one development value that does persist, in `localStorage` under `poseidon.dev.selection`. It records which history to boot, never any history.

Unrelated browser UI preferences can still use their existing browser storage.

## Seed authority

`apps/web/src/dev/mock-data.ts` owns one explicit 30-dive scenario. The smaller presets are prefixes of the same sequence.

The seed uses:

- the canonical Mexican-Caribbean content pack;
- canonical current dive sites and their region/coordinate metadata;
- canonical current creature IDs and runtime artwork;
- real `PoseidonStore.createDive()` validation;
- real `createUserCreature()` for one deliberate unlisted-creature example;
- deterministic IDs and timestamps.

The data covers Cozumel and Playa del Carmen, repeated sites and encounters, same-day pairs, multiple trip periods, highlights, sparse notes, operators/buddies, Atlas density, Collection density and repeated Creature Detail history.

Canonical sites and creatures are resolved by exact current content names. A removed/renamed dependency throws during seeding rather than silently substituting another record.

Only personal history is synthetic. The marine catalogue and art are production data.

## Data & Backup

The real Data & Backup screen works in mock mode because it talks only to the active `PoseidonStore`.

- export serializes the current in-memory record;
- merge/replace affects only the current in-memory record;
- real account history and the local Firestore shadow are unreachable;
- reload restores the selected seed.

The Account section is rendered only when an auth context is present, so it is absent in the unauthenticated mock root without teaching the screen about Firebase or mock persistence.

## Verification

`npm run gate` includes the dedicated mock browser acceptance probe.

Focused commands:

```bash
npm run test --workspace @poseidon/web
npm run test:mock
```

Coverage includes:

- exact `0 / 3 / 5 / 15 / 30` dive counts;
- deterministic reconstruction;
- smaller-preset prefix stability;
- canonical sighting resolution plus the deliberate user-created creature;
- normal create/edit/delete behavior in memory;
- reconstruction resetting session mutations;
- the production hard guard on mock mode;
- selection resolution order, `?mock=off`, persistence and rejection of unusable stored values;
- browser confirmation that sign-in is bypassed;
- browser access to the real Data & Backup screen;
- browser confirmation that the badge switches preset and that the choice survives a parameter-free reload;
- failure on any Firebase/Firestore/Auth module request or network request in mock mode.

The browser probe runs the **ordinary** development server and selects mock history at runtime, then records all requests. It therefore catches both accidental Firebase network traffic and local Vite dependency-module loading such as `firebase/auth` or `firebase/firestore`. Running against the normal dev server is the point: the Firebase boundary now has to hold on the same site that can also load Firebase.

## Extension rules

When extending the scenarios:

- keep the sequence deterministic;
- preserve `0 / 3 / 5 / 15 / 30` unless there is a deliberate tooling change;
- make smaller histories prefixes of larger histories where practical;
- use canonical content rather than synthetic marine taxonomy;
- use normal domain methods rather than hand-writing persisted JSON;
- add data only when it exercises a meaningful product state;
- do not persist mock history;
- do not add Firebase emulator dependencies;
- do not scatter mock checks through product screens;
- keep the badge styled by its own scoped stylesheet rather than brand tokens, so development chrome never reads as product UI and never becomes a brand-migration concern;
- do not add production-visible debug controls.

Issue #21 remains a separate brand-system migration. Mock tooling must preserve whichever production token system and screen design is current when the branches reconcile.
